# Plan 0.0.19 (direction record) — H-line: MCP adapter for file/exec/screen

Status: **direction record, not an implementation plan.** Nothing here starts
code, adds a dependency or lifts a `[no]` on its own. It records the dated
owner direction and the controller's ordering decision so the next W0/W1 pass
has a starting shape. The full plan must still pass the 6/6 completeness
checklist in `PRD_01_23` before any W2 work.

Owner direction (2026-11-08, recorded in `PRD.md` roadmap block): the harness
line reopens **in this repository**, omp-style. minicon-harness becomes the
**companion of other harnesses**: external agents (Claude Code, DSH, OpenCode,
Hermes, Orca …) should be able to mount its tools as their local
computer-use / execution backend.

## Shape (to be refined by W0/W1)

```text
minicon-harness.com (worker core)         UNCHANGED: three tools, bounded
                                          loop, one file, no plugin host,
                                          every core [no] inherited
└── mcp adapter  (new binary or
    subcommand beside the core)
    ├── exposes file / exec / screen as MCP tools over stdio
    ├── translation only: MCP tool call -> one bounded core invocation,
    │   tool result -> MCP response; every bound, grant, receipt and
    │   readback of the core passes through unchanged and unweakened
    ├── grants map to MCP: --root / --allow-cmd / --allow-screen are the
    │   whole policy, supplied by the mounting client, no policy engine
    ├── [no] in the adapter: plugin host, scripting surface, streaming,
    │   its own model loop, network listener (stdio only in the first
    │   slice), any widening of file/exec/screen semantics
    └── evidence: adapter ops are logged with the same typed rows as the
        core, so the independent-reader rule (E2) still applies
```

## Why this is not a violation of the standing [no]

`PRD.md` keeps `no plugin host, permission policy, streaming, MCP, a
scripting surface` **inside the worker core**. The adapter sits beside the
core like the Cosmopolitan trampoline does: it translates a protocol, it does
not extend a tool. Each core refusal must refuse identically through the
adapter — that equivalence is the acceptance invariant, and the plan's first
W1 test list should be exactly those equivalence rows.

## Ordering (controller decision 2026-11-08)

Hands before mouth: the MCP adapter (0.0.19) precedes the gateway sidecar
(M-line, ≥0.0.20) because the adapter is the gateway's first real consumer
and the cheapest proof of the companion positioning. The CU line keeps its
own candidate pool between versions; nothing in this record pauses it.

## Open questions for W0/W1 (non-exhaustive, to be upserted)

1. MCP transport for the first slice: stdio only? (assumed yes; Streamable
   HTTP deferred with a named unlock)
2. One-shot vs long-lived process model: does the adapter hold a resident
   core, or exec per call? Evidence must bound resident memory either way.
3. Schema naming: MCP tool names/JSON schemas for the three tools and the
   `screen` verbs — reuse `cu-abi` wire names verbatim or rename for MCP
   conventions (recommend: verbatim, so one contract document stays
   authoritative).
4. Packaging: does the adapter ship inside the `.com` ZipOS overlay or as a
   second artifact in the Release? (recommend: second artifact; the core
   binary budget stays untouched)
5. Qualification: three-OS CI must mount the adapter from one real external
   client (any MCP-capable CLI) and drive one journey step through it.

# Controller supplement (2026-11-08, same day) — open questions answered

The controller answers the five open questions below. Each answer is a
controller decision (T8 D10) with its reason; the owner keeps a veto. These
answers are what the W0 pass must confirm or falsify — if W0 evidence
contradicts one, the plan is upserted and re-checked 6/6 before W2.

## Q1 transport: stdio only, first slice — **decided: yes**

Streamable HTTP needs a listener, which is exactly the `[no]` shape (network
surface + lifecycle + auth questions) the first slice must not open. stdio
is also the only transport every listed consumer (Claude Code, DSH, OpenCode,
Cursor-class clients) supports for local servers. **Unlock for HTTP:** a
dated owner request plus a threat-model note in this file; the M-line
gateway (≥0.0.20) is the natural place for any listening surface anyway.

## Q2 process model: resident core, one per adapter — **decided: resident**

- The adapter holds **one resident `CuHost`/core instance** for its lifetime.
  Rationale: `screen` is stateful by design — the 0.0.12 generation/frame
  contract, the 0.0.13 wait budget and the 0.0.16 effect readback all bind
  to the host state. Exec-per-call would reset the generation every request
  and quietly break `act:control`/`observe`/`effect` sequencing, which is
  the adapter's main value over a raw script.
- Bound: the core's existing bounds are the bound. The adapter adds **no
  buffer it does not pass through**, one request in flight at a time (MCP
  stdio servers are request/response), and a hard cap on the JSON-RPC frame
  size it will read (proposal: 1 MiB, matching the largest legitimate
  `screen` evidence envelope; the W0 pass fixes the number from the shipped
  evidence shapes).
- Evidence: adapter logs its own RSS at startup and after each call in the
  same typed-row format as the core, so the resident-memory question is
  answered by measurement, not assertion.

## Q3 schema naming: `cu-abi` wire names verbatim — **decided: verbatim**

One contract stays authoritative: the tool/parameter names, verdict
vocabulary (`performed/refused/stale/unknown/unsupported/not_performed`),
receipt shapes and refusal reasons are the `cu-abi` wire names, unchanged.
MCP clients see `tools/list` entries named `file`, `exec`, `screen` with the
exact parameter objects the wire already publishes (`src/wire.rs`
`tool_definitions`). Cost: names are PascalCase-ish rather than MCP-idiomatic
snake_case in places; benefit: every existing test, reader and PRD statement
about the wire remains true through the adapter, and the equivalence
invariant (below) is mechanically checkable.

## Q4 packaging: second artifact in the Release — **decided: second artifact**

- The adapter ships as **`minicon-harness-mcp` (or a `--mcp` subcommand of
  the same binary if W0 shows the size cost is < ~50 KiB after dead-code
  elimination)** — decided at W0 exit, not now.
- Either way the core `.com` budget (PRD_01_01, 6,553,600) is untouched;
  a separate artifact gets its own sidecar + receipt row, and mounting
  clients install exactly one thing.
- Default recommendation stands: second artifact, signed like the rest.

## Q5 qualification: one real client per OS — **decided: Claude Code headless + a scripted raw JSON-RPC client**

Three-OS CI cannot assume a specific external CLI is installed, so the gate
has two tiers, both required on every OS:
1. **Raw JSON-RPC mount** (deterministic): CI drives the adapter over stdio
   with scripted initialize/tools-list/tools-call frames and an independent
   reader recomputes the equivalence rows below.
2. **One real client, at least Windows** (the market gap the owner named):
   mount from a real MCP-capable CLI in the Windows journey job, drive one
   `observe` + one `act` through it. If the client cannot be installed on
   the runner, this tier is a named, dated gap in the acceptance record —
   not silently dropped.

## The acceptance invariant (equivalence rows — the W1 test list)

For every core behaviour, adapter-through behaviour must be **identical or
a named translation**:

| # | Core behaviour | Adapter expectation |
|---|---|---|
| E1 | any bound refusal (path escape, type bound, wait ceiling…) | same verdict + same reason text through MCP |
| E2 | `screen` verdicts incl. `unsupported` on non-Windows cells | same verdict; no cell gains or loses a capability through the adapter |
| E3 | generation/frame sequencing (`act:control` after `observe`) | sequencing preserved across separate MCP calls against the resident core |
| E4 | grants: `--root/--allow-cmd/--allow-screen` absent ⇒ refusals | identical refusals; the adapter adds no grant of its own |
| E5 | evidence rows + receipts | byte-identical typed rows inside the MCP response content |
| E6 | `[no]` rows (plugin host, policy engine, streaming, listener) | adapter itself implements none; any attempt is a named refusal, not a silent ignore |
| E7 | unknown JSON-RPC params / extra initialize fields / `ping` at any time | ignored (not errored) per JSON-RPC tolerance; `ping` answered before and after `initialized` |

## W0 pass 11 record (2026-11-08) — findings

1. **MCP spec (2025-11-25 revision, basics confirmed against 2025-06-18)**:
   JSON-RPC 2.0 over stdio, newline-delimited UTF-8 frames; `initialize`
   request → server responds protocolVersion/capabilities/serverInfo →
   client `notifications/initialized`; then `tools/list` (static ⇒ no
   `listChanged`, no cursor) and `tools/call` `{name, arguments}` →
   `{content:[{type:"text",…}], isError}`. Protocol errors are JSON-RPC
   error objects (-32700/-32600/-32601/-32602/-32603); **application
   refusals are `result.isError:true` with the reason as text** — which maps
   1:1 onto the core's typed refusals (a core refusal is an application
   outcome, not a protocol error; E1 keeps the reason text verbatim).
   Version negotiation: server answers its own latest if the client's is
   unknown; the adapter pins the one revision it was W0-verified against.
   `outputSchema`/`annotations`/pagination/tasks/elicitation: not needed for
   the first slice; their absence is spec-legal.
2. **Envelope measurement (this machine, real WorkBuddy tree)**: the largest
   legitimate no-capture observe (`a11y` scan, 43-node tree + windows +
   displays) produced an **11.5 KiB** JSON result (9.2 KiB evidence + 1.9 KiB
   text). Bounds already cap rows (400 a11y nodes), so the worst legal case
   is ~2-3× that. **Frame cap decided: 1 MiB** (Q2) — 40× headroom over the
   measured worst case; captures never enter the response (path reference
   only, unchanged).
3. **Spike finding (from the repo's own `cu_orchestrate` example)**: the
   core already has everything the adapter loop needs — `CuHost::
   invoke_json(request) -> CuResult{verdict, evidence, text}` is exactly a
   tool call/response. The adapter is: read line → parse JSON-RPC → route
   (initialize | tools/list from `wire.rs::tool_definitions` | tools/call →
   invoke_json) → write line. No async, no crates: std stdin/stdout
   line-loop, one request in flight.
4. **omp (oh-my-Pi) reference study — adopt the position, not the mass**:
   omp is ~80k lines of Rust *inlined* into the agent (embedded shell, AST,
   PTY) plus 31 tools — the opposite bet of this repo's bounded three-tool
   core. What we take from it: (a) the **companion positioning** (serve
   other harnesses rather than grow features) is validated demand; (b) its
   MCP layer's 250ms start gate + DeferredMCPTool exists because omp servers
   are *heavy processes* — our thin resident adapter over a bounded core
   has no such cost, confirming Q2's resident choice; (c) its multi-registry
   MCP state machine (reconnect, circuit breaker) is client-side machinery
   we must NOT need. `[no]` rows unchanged: nothing of omp's plugin/marketplace/
   hooks surface enters this repo.
5. **Risk found**: Claude Code-style clients send `initialize` with extra
   fields (elicitation/tasks caps) and may probe with `ping` before
   `initialized` — the adapter must ignore unknown params (not error) and
   answer `ping` at any time. Added to the E-table as E7.

## Owner direction

moltbaby's `corp-engine/llmgate` is **retiring**: development paused on

runtime: the retired stack is not a dependency of this repository.

## The filter decides everything

PRD roadmap defines M-line as "a protocol converter and router: no tool
execution of its own, no policy engine, no plugin runtime. Management UI is
NOT built here (agenterm owns the family entry/management surface; the
gateway exposes an inspect API only)", with loopback-only listening.

**Therefore migration is a subtraction, not a move.** Of llmgate's twelve
control planes, only converter / router / read-only-inspect ones survive as
candidates; the rest are precisely the policy engine, plugin runtime, and
management surface PRD forbids. Carrying them over would violate `[no]`
within the first W0 pass.

## Inputs from the retired stack's own design record

Three conclusions from moltbaby `docs/` are worth carrying as constraints,
not as code:

1. **Keys stay on the Host** — `ujs/practice/uxe/HOST_ABI.md` §7.1 `host_llm`
   (planned, unimplemented) already says BYOK, key never in wasm / UJS
   globals / logs, OpenAI-compatible chat subset, bytes + small schema,
   timeout and cancellation on the Host. This agrees with M-line's
   loopback-only converter shape and with plane 3 above. ujs is still in
   development: **not a dependency, not on the critical path**.
2. **The four-layer split** (L1 parameters / L2 rules / L3 decision
   algorithms / L4 executor) explains the rejections above: M-line keeps
   L1 and L4; L2/L3 are the policy engine it must not own.
3. **Safety comes from replayable comparison, not restricted
   expressiveness.** This is the same idea as this repo's typed evidence
   rows and the E2 independent-reader rule. If M-line ever records routing
   decisions, an independent reader must be able to recompute them.
