# 0.0.21 — background-first act:control (working-tree hardening)

Owner mandate 2026-11-10: computer use must operate windows without requiring
the foreground — minimized or background windows are first-class targets, and
stealing focus is a defect. This version closes three of the four named gaps
in PRD.md's "Background-first operation" section and hardens the working tree
that already pointed that way.

## What shipped

1. **`act:control` default is the semantic invoke (0.0.21 contract change,
   owner-directed).** With no mode flag the resolved a11y node's native
   invoke fires — UIA `InvokePattern` first, MSAA `accDoDefaultAction` as the
   declared fallback — never the pointer. `press: true` and the new
   `hover: true` are explicit-only; the default `source: "controls"` call is
   a named refusal that names the two real alternatives, never a silent
   pointer fallback. The receipt publishes `mode`
   (`invoke-default`/`invoke`/`set-value`/`press`/`hover`),
   `invoke_defaulted`, `invoke_path`, and — for the explicit pointer modes —
   `foreground_before`/`foreground_after` (rank-3 disclosure, both in
   evidence and in the text). cu-abi stays 1.0: one additive param
   (`hover`), additive evidence keys, no shape removed.

2. **UIA InvokePattern invoke (the Chromium DOM path).** Chromium's MSAA
   `accDoDefaultAction` returns S_OK without a DOM effect on self-drawn
   buttons, so an S_OK alone is not evidence. The invoke now tries
   `IUIAutomationInvokePattern::Invoke` on the element matched by
   `Name` (+ `ControlType` when the published MSAA role has a fixed
   counterpart); a UIA miss/failure falls back to MSAA with both reasons in
   the result. The matched-path tag travels in evidence
   (`uia-invoke-pattern` | `msaa-default-action`).

3. **Minimized `-32000` remap.** A minimized window's live rect is the
   -32000 tombstone. `windows()` now publishes the saved
   `WINDOWPLACEMENT.rcNormalPosition` (workspace→screen corrected by the
   primary work-area origin); the a11y scan translates every node rect by
   `normal_origin − live_origin` and discloses the basis change in
   `a11y_reason`. The placement is captured, never applied — observe never
   restores, raises or activates (PRD hard bar). Multi-monitor normal
   positions keep the documented work-area approximation; the disclosure
   says so.

4. **Working-tree review findings fixed (the diff under review had two
   latent P1s in `uia_kick`):**
   - `IID_IUIAUTOMATION` was `{30cbe57d-d9cf-4511-9200-064903d2f854}` — not
     a real GUID (the SDK declares
     `{30cbe57d-d9d0-452a-ab13-7ac5ac4825ee}`), so `CoCreateInstance`
     failed on every call and the kick was a silent no-op; the 400 ms
     empty-tree retry masked it as a delay.
   - `ElementFromHandle` was called at vtable slot 3 — that slot is
     `CompareElements`; slot 6 is `ElementFromHandle`. With the IID fixed,
     the old slot would pass the raw HWND as an `IUIAutomationElement*`.
   Both are now pinned by unit tests against the SDK header values
   (`uia_guids_match_the_sdk_header_byte_for_byte`).

5. **Tests.** `a11y_clip`/`to_line` (one-line-per-node + JSON frame
   integrity), the minimized-placement pure helpers, the UIA GUID/type pins,
   the default-mode admission matrix, invoke evidence (`mode`,
   `invoke_defaulted`, `invoke_path`, fallback and dispatch-failure
   verdicts), the resident-MCP-host composition proof
   (`the_screen_host_is_resident_across_stdio_calls`), and a test seam:
   `CuHost`'s a11y invoke backend is a named dependency, stubbed in tests so
   no unit test touches a desktop.

## Deliberately out of scope (recorded, not decided)

- A semantic invoke backend for `source: "controls"` (e.g. `BM_CLICK` via
  background-safe window messages, PRD rank 2). The default there refuses
  with guidance instead.
- Minimized-window nodes carrying `STATE_SYSTEM_OFFSCREEN`/`INVISIBLE` may
  trip the `a11y_node_operable` veto; whether that needs window-awareness is
  an on-desktop question, verified against real windows before touching the
  predicate.
- `act:click`/`act:drag` foreground disclosure (act:control's pointer modes
  disclose now; the standalone verbs predate this work).

## Verification (on-desktop, 2026-11-10, real windows via minicon-harness-mcp stdio)

All runs drove the release `minicon-harness-mcp --allow-screen` over stdio
against the live desktop (ZCode `hwnd=19798326`, WorkBuddy `hwnd=371595850`,
both Chromium-class `Chrome_WidgetWin_1`).

**Minimized-window loop (the PRD hard bar):**
- `observe a11y` on minimized WorkBuddy publishes the full tree (204-256
  nodes; the UIA kick + bounded retry wakes the renderer). The remap note is
  disclosed (`window is minimized: raw rects are tombstone- or client-basis
  ...`), and coordinates land on the placement basis (document 840x1014 at
  0,0; window controls at 702..840,0 — correct for an 840-wide window).
- Provider basis is genuinely inconsistent run-to-run (Chromium publishes
  tombstone-translated or client-basis raws depending on its cached window
  origin), which is why the per-node detection (`minimized_node_screen_pos`)
  is required; a uniform delta poisoned one of the two shapes on real data.
- Default `act:control` invoke (no mode flag) on a minimized-tree button:
  verdict=performed, `mode=invoke-default`, path disclosed
  (`invoke via msaa-default-action; uia did not run: no UIA element matches
  ...` — see the minimized-UIA finding below), and `GetWindowPlacement`
  probes before/after show `showCmd=2` (minimized) unchanged — zero restore,
  zero activation. Foreground stays ZCode throughout.
- DOM effect proven by tree diff twice: invoking `收起侧边栏` renamed the
  toggle to `展开侧边栏` (sidebar collapsed); invoking again restored it.

**UIA InvokePattern path (task 3):** on a visible (non-minimized) window the
UIA tree is fully populated (probe: 108 elements with names/bounds vs 8 shell
elements minimized). Default invoke on the visible window ran
`invoke via uia-invoke-pattern` (receipt), and the next observe showed the
toggled state — the InvokePattern path reaches Chromium's DOM. Same on ZCode:
`展开侧边面板` invoked via `uia-invoke-pattern` on the background ZCode
window, effect readback showed `收起侧边面板` plus the opened panel's nodes,
then restored.

**Finding (disclosed, not hidden): Chromium steals the foreground on a
default action for a *visible background* window.** Invoke on background
ZCode while WorkBuddy held focus moved the foreground to ZCode (window rows
before/after in the same MCP session). This is Chromium's internal
`DoDefaultAction -> Focus()` behaviour on both the UIA and MSAA dispatch
paths — not addressable from the harness, and a minimized HWND cannot be
activated, so the minimized loop stays at zero focus change (verified).
0.0.21 therefore publishes `foreground_before`/`foreground_after` and a
`focus_changed` flag (plus a readback `focus changed: X -> Y` line) on every
semantic invoke and set_value receipt: a steal is a visible defect, never a
silent success.

**Background readability:** `observe a11y` published the background ZCode
tree (142 nodes while WorkBuddy held focus) and the minimized WorkBuddy tree.

**Known approximations:** `rcNormalPosition` can be stale for Chromium
windows (Chromium keeps its own bounds; moving a window via SetWindowPos did
not update the placement), so the minimized remap is placement-basis and the
scan note says so. The MCP stdio driver used for verification lives outside
the repo (session workspace); the probe examples already in `examples/`
covered the raw COM surface.

**Suite:** 230 lib + 13 integration tests green (`cargo test`), version
0.0.21 pinned across Cargo.toml / release-policy.json / ape-version.rc /
banner tests.
