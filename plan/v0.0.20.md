# Plan 0.0.20 -- M-line: LLM gate skeleton

Status: **implementation plan, 6/6 confirmed (D13, 2026-11-09).** The
contract is owned by [`prd/PRD_01_27_llm_gate.md`](../prd/PRD_01_27_llm_gate.md)
(`[_]`, drafted 2026-11-09); this file owns the work breakdown, tests,
packaging and gates. No code, dependency, `[no]` change or `[v]` capability
claim exists yet. W2 is authorised by D13 (`PRD_01_24`); the two questions
that still need measurement (G1, G2/G7) are entry criteria of W3/W4 with
decided fallbacks (section 12).

Owner direction (2026-11-09): build our own **LLM gate** in this repository,
pooling the tuple **(provider-and-account, model, modelArgs, http-proxy)** and
using it to bind agents into workflows. `PRD_01_27` refines that tuple into
three axes -- **endpoint x credential x egress** -- so the tuple stays the
product, not the storage shape. Motivating failure: a single process-wide
`HTTP_PROXY` in a client (OpenCode desktop) is all-or-nothing, cannot be
scoped per provider/account, and breaks when the proxy is on loopback. The
gate exists so the **egress decision is data, not an environment variable**.

## 1. Why 0.0.20 is the gate

1. **The roadmap already says so.** `PRD.md`'s recorded roadmap assigns
   `>= v0.0.20` to the M-line gateway sidecar. A product review dated
   2026-11-09 proposed the H-line closeout for this slot; the owner direction
   and the recorded roadmap take precedence (correction recorded in that
   file; decision D12 in `PRD_01_24`).
2. **The H-line gap is a precondition, not a theme.** `v0.0.19` published the
   core but left `minicon-harness-mcp` out of the Release archives. The
   adapter is the gate's first real consumer ("hands before mouth"), so its
   packaging closes in 0.0.20 W0 as release engineering. It adds no
   capability and does not become the version topic.
3. **The gate is the smallest surface that solves a measured problem.** The
   OpenCode proxy failure is not fixable inside the client; it is fixable by
   a loopback endpoint that holds the account/model/args/proxy decision.

## 2. Scope of 0.0.20

| In 0.0.20 | Out of 0.0.20 (named, not forgotten) |
|---|---|
| `minicon-gate` binary, one loopback listener | a second listener / non-loopback by default |
| config load, atomic reload, revision pinning | config CRUD API or UI |
| three-axis pool: endpoints, credentials, egress, lanes (`PRD_01_27`) | provider metadata table (provider is a label) |
| credential secrets `env` / `file`; `"client"` pass-through | `oauthFile`, `command`, encrypted store |
| lane expansion: `credentialOrder` x `egressOrder`, deterministic | tag queries, weighted selection, health scoring |
| gate-established egress tunnels (`direct` / `env` / explicit URL + `noProxy`) | proxy auto-discovery, PAC, SOCKS |
| per-axis cooldown that reorders, never drops | budgets, rate limits, admission policy |
| workflow declarations + node-level `modelArgs`/`egress` + `/resolve` | workflow execution, scheduler, step retry |
| `/v1/chat/completions` non-stream + SSE pass-through | `/v1/responses`, `/v1/embeddings` |
| `/v1/models`, health, read-only inspect, evidence rows + JSONL mirror | management verbs, metrics UI |
| `openai-chat` protocol only | `anthropic-messages`, `openai-codex`, `harness` lanes |
| reader script + three-OS CI | any new core tool or CU verb |
| H-line adapter as a signed second artifact (precondition) | |

One theme, one exit criterion: **a config with two providers, two credentials
and two egresses routes a request, a 429 cools the credential while `direct`
stays eligible, and the reader recomputes the expanded order and every skip
from the revision alone.**

## 3. Architecture (contract: `PRD_01_27` "Three planes")

```text
client --(loopback, never proxied)--> gate --(lane egress)--> upstream

definition  endpoints, credentials, egress, lanes, agents, workflows   data, revisioned
resolution  intent -> expanded, ordered candidates                     pure function, no I/O
transport   one attempt: secret, tunnel, dispatch, classify            bounded, one lane at a time
```

- The gate **routes one model call**. No conversation, no model loop, no
  tools, no step scheduling.
- A workflow is **declared here and executed elsewhere**; the gate validates,
  resolves every node, serves the plan, and never advances a node.
- Every `[no]` in `PRD.md` stays literally true.

Rejected alternative (recorded so it is not re-litigated): an executing gate
collapses pool, orchestrator and harness into one process -- the retired
`mapp`/`dispatch` shape -- and takes the M-line `[no]` rows with it.

## 4. The contract deltas this plan must implement

The full statements live in `PRD_01_27`; each item below is the work-bearing
consequence, with its acceptance row.

1. **Three axes, not a flat lane.** `endpoint {provider, baseURL, protocol,
   headers?}`, `credential {secretRef, label, scope?}`, `egress {proxy,
   noProxy, timeouts?}`; a lane is `endpoint x credential x egress + model +
   modelArgs + limits`. A flat lane would cool a whole row when one axis
   failed; the reader must be able to name **which axis failed**. (M1, M15)
2. **Expansion is the Kronecker product**: credential outer, egress inner,
   both in declared order, deduplicated by
   `(endpoint, credential, egress)`. Deterministic, so the reader recomputes
   it from the revision alone. A named lane is the product of one. (M15)
3. **Precedence** `gate defaults < credential.scope < lane < agent < workflow
   node < request`; objects merge deep, headers case-insensitive, arrays
   replace. `proxy`, `credential`, `endpoint`, `baseURL`, `protocol`, `model`
   are operator-only; a workflow node may set `modelArgs` and `egress` only.
   (M2, M3)
4. **The tunnel is established by the gate**, not by the HTTP client's own
   proxy support: a per-lane egress cannot be expressed through a process-wide
   or agent-wide proxy setting. `noProxy` is mandatory for an explicit egress
   (default `localhost,127.0.0.1,::1`); an egress pointing at the gate's own
   listener is a load-time refusal; a 407 cools the **egress**, not the lane.
   (M5, M14)
5. **Fallback and cooldown**, exactly the `PRD_01_27` table:

   | Outcome | Verdict | Fallback | Axis cooled |
   |---|---|---|---|
   | upstream 2xx | performed | stop | none |
   | upstream 429 | refused | yes | credential, 60 s |
   | upstream 5xx | refused | yes | egress, 30 s |
   | upstream 401 / 403 | refused | no | credential, 300 s |
   | upstream 400 / 404 / 422 | refused | no | none |
   | connect / TLS / tunnel failure | unknown | yes | egress, 60 s |
   | proxy 407 | unknown | no | egress, 300 s |
   | secret unreadable | unknown | no | credential, until config change |
   | non-stream body over bound | unknown | yes | lane, 30 s |
   | config revision changed mid-request | stale | no | none |

   A non-429 4xx never falls back. Cooling **reorders** the candidate list,
   never drops a lane, so the reader recomputes demotion, not absence. A
   cooling-plus-queue-full state with zero candidates is a local `429` with a
   named reason, never a silent downgrade to another pipe. (M4, M8, M16)
6. **Evidence row** carries `triggered_by` / `trigger_reason`, the three axis
   ids, `egress_host` (host:port, never a URL), `lane_state_before`/`_after`
   and `cooldown_until`. A **JSONL mirror is required** whenever
   `events.mirror` names a path: the ring alone cannot support offline
   recomputation after the process exits. (M6, M10)
7. **Bounds**: 256 endpoints, 256 credentials, 64 egress, 512 lanes, 256
   agents, 64 workflows x 64 nodes; **expanded candidates per agent <= 32**
   after the product; everything else per `PRD_01_27`. (M12)

## 5. Implementation shape

- **std-only concurrency**: one accept thread, a fixed worker pool (default 4,
  max 16), one per-lane counting semaphore, one bounded queue per lane. No
  async runtime, no new crates (`serde_json` + `ureq`, like the core).
- **HTTP server**: hand-written bounded parser on `std::net::TcpListener`
  (request line + headers + content-length body; chunked requests refused
  with `bad_body`). The MCP adapter proved this discipline on stdio; this is
  the same on TCP.
- **Egress tunnel**: the gate opens `TcpStream` to the proxy, writes
  `CONNECT host:port`, checks `200`, then hands the connected stream to
  `ureq` through its custom `Transport` seam (G1 verifies the seam; the
  fallback is a minimal request/response path over the tunnel). `direct` and
  `env` reuse `wire.rs`'s transport unchanged.
- **Files**:

```text
src/gate.rs                config, pool + expansion, resolver, router, evidence, server
src/bin/minicon-gate.rs    thin main: --config, --allow-non-loopback, banner
src/wire.rs                additive proxy-capable transport (core untouched)
scripts/gate-verify.py     independent reader (expansion, order, cooldown, redaction)
.github/workflows/gate-journeys.yml   three-OS loopback tier (W4)
```

- **Crash rule**: a worker panic fails that request with `502 unknown`, never
  the process. `Ctrl+C` drains in-flight requests up to 10 s, then exits.

## 6. Refusal catalog (named constants; local refusals only)

| Code | Where | Meaning |
|---|---|---|
| `unknown_model` | 400 | `model` is not `gate/<agent>` or `gate/lane/<id>` |
| `unknown_agent` / `unknown_lane` | 400 / 404 | id does not exist |
| `unknown_endpoint` / `unknown_credential` / `unknown_egress` | load | dangling reference in a lane or order list |
| `unknown_workflow` | 404 | workflow id does not exist |
| `protected_field` | 400 | a request/node override sets an operator-only field |
| `bad_body` | 400 | not one JSON object / chunked request |
| `body_too_large` | 413 | request body over the cap |
| `queue_full` | 429 | lane queue at its bound |
| `attempt_budget` | 429 | `budget.maxAttempts` exhausted |
| `no_candidate_available` | 503 | every expanded candidate is cooling or queue-full |
| `secret_unreadable` | 503 | env unset / file unreadable, named without content |
| `upstream_unreachable` | 502 | transport failure on the last candidate |
| `stale_config` | 503 | revision changed mid-request |
| `protocol_unsupported` | 400 | a shape `openai-chat` cannot express |
| `not_in_this_slice` | load / 400 | `oauthFile`/`command` secrets, `harness` lanes, weighted select |
| `expansion_over_bound` | load | expanded candidates exceed 32 |
| `egress_self_loop` | load | an egress host equals the gate listener |

Load-time refusals print file + JSON path + reason to stderr and exit non-zero;
a gate never starts on a config it only half-understands. Local refusals use
the `PRD_01_27` error body (`error.message` / `type: gate_refusal` / `code`);
**upstream statuses and bodies pass through verbatim** with the `x-gate-*`
headers added.

## 8. Test and CI plan

1. **Unit** (three OSes, `cargo test`): precedence, expansion, refusal
   catalog, bounds, redaction, revision hashing. No network.
2. **Loopback tier** (three OSes): a real `minicon-gate` plus an in-process
   **stub upstream** (scripts 2xx/429/500/401/timeout/SSE and records exactly
   what it received). Drives M1-M4, M7-M12, M14-M16 on the actual wire.
3. **Proxy tier** (Windows + Linux): a stub HTTP proxy that counts `CONNECT`
   tunnels and can emit 407, proving per-egress selection, `noProxy` bypass
   and egress-axis cooldown (M5, M8).
4. **Real client tier** (at least Windows): the core itself
   (`minicon-harness --base-url http://127.0.0.1:8787/v1 --model gate/...`)
   completes one two-turn conversation; an OpenCode mount is recorded as
   evidence when present, never required.
5. **Reader**: `scripts/gate-verify.py` recomputes (a) the expanded candidate
   order, (b) the chosen attempt with every skip/demotion reason, (c) egress
   hosts, (d) redaction, from the mirrored events plus the config snapshot;
   CI fails on mismatch or scanner hit.

**Deviations, for the controller to upsert.**

1. **`credentials[].endpoint` (plan 4.8) vs `scope` (PRD_01_27).** The plan
   gives a credential an `endpoint` field; the contract gives it a `scope` and
   does not bind it to one endpoint. Implemented: `endpoint` is **parsed and
   checked** against every lane that names the credential
   (`credential_endpoint_mismatch`), and `scope` is an optional object merged
   at the lowest precedence layer. Both work; the contract is not changed.
   Needs a decision on which one the fixture should teach.
2. **`ureq` and the tunnel.** Handoff rule 1 caps dependencies at `ureq`. The
   G1 question is answerable without that cap being broken: `ureq` 2.12.1
   exposes `AgentBuilder::tls_connector` over the public `TlsConnector` trait,
   so the gate can hand `ureq` an already-CONNECTed stream. The catch is that a
   custom connector must be written against `rustls` types, which makes
   `rustls` an explicit dependency for the **gate artifact only** (the core's
   `[no] any new crate` is untouched, and `ureq` already links `rustls`
   0.23.46 today). This is a W3 entry decision, not a W2 one, but it is the
   one place where "no new crates" cannot be read literally without giving up
   per-lane egress. See the W3 record for the measurement.
3. **`client` credential.** G6 decided `allowedHosts` is mandatory. The section
   4.8 fixture predates that decision and omitted the key, so the fixture
   carries one added line (`"allowedHosts": ["relay.internal.example"]`).
   Without it the fixture is refused, which is the decision working.
4. **`defaults.timeout` vs `egress.timeouts`.** The fixture uses
   `defaults.timeout` (singular); the axis entries use `timeouts`. The parser
   accepts `defaults.timeout` as written and stores it as `Timeouts`; the
   contract's `timeouts` spelling is accepted on an egress. Needs one spelling.
5. **`workflow.edges[].kind`** appears in an earlier draft of the plan but not
   in the contract; the parser accepts and ignores it rather than refusing an
   unknown field there.

**Next entry point.** W2 continues with the loopback listener and the
non-stream request path; the G1 spike is still W3's first task as the plan
says, and the ruling above shortens it (the seam exists; the work is the
connector).

### W3 record (2026-11-09, complete)

**G1 disposed, and the ruling shortened the work.** The spike
(`tests/g1_spike.rs`) proves the `ureq` 2.12.1 `TlsConnector` seam exists and
receives an established stream: `AgentBuilder::tls_connector` takes a custom
connector, the connector gets a `Box<dyn ReadWrite>`, and it can refuse.
That is the answer to *"can the gate own the CONNECT and still let ureq speak
HTTP?"* -- **yes**. What the spike also showed, and what changed the design:

> `ureq` only calls `tls_connector` on **https**. For an **http** URL it goes
> through its own proxy path and forwards the request with an absolute URI.

So the connector seam cannot carry per-lane egress for plain-http upstreams.
The shipped design therefore uses `ureq::AgentBuilder::proxy(ureq::Proxy)` with
a **per-attempt agent**: one agent carries exactly one egress, which is the
property the contract actually requires ("the tunnel is the unit of the per-lane
decision"). G1's fallback branch was not needed.

| Item | W3 outcome |
|---|---|
| tunnel plane | `src/gate/tunnel.rs`: route resolution (`direct` / `env` / explicit), `noProxy` bypass with exact and `.suffix` entries, proxy URL parsing with userinfo, `CONNECT` construction with Basic auth, pure-std base64, self-loop refusal |
| egress wiring | `transport.rs` builds one agent per attempt with that attempt's proxy, so no request inherits another lane's pipe |
| proxy answer | a `CONNECT` refusal is `Outcome::ProxyRejected`, **never** passed to the client as an upstream answer; a 407 cools the egress and stops the chain (D5) |
| retryable statuses | a 429/5xx now actually **falls back** before any pass-through; non-429 4xx and 401/403 stay final. This was a real defect found by the W3 tests |
| attempt budget | `completed` counts **finished** attempts, so a decision to stop never burns a budget slot |
| cooling | demote-to-back with the reason, expire by TTL, clear on config change; proven as a pure function (M16) and over the wire |
| H-line | untouched (M13 stays a W4 item) |

`gate_loopback` (6) and `gate_tunnel` (3) integration tests. Four consecutive
full runs are clean. M4-M7, M10 (chain half), M14 and M16 now have tiered

**Deviations.**

1. **`ureq::Proxy` per attempt instead of a gate-written `CONNECT`.** The
   contract says "the tunnel is established by the gate". With `ureq` owning
   HTTP there are two shapes: a gate-written tunnel handed over through
   `tls_connector` (https only), or a per-attempt agent whose proxy `ureq`
   connects (`ureq` writes the CONNECT, with `Proxy-Authorization` from the
   URL). The second is the one that also works for http, and it still makes the
   decision per lane. The gate still owns route selection, bypass, redaction and
   classification; it does not own the socket. This needs a controller ruling on
   the contract sentence, not a silent reading.
2. **Proxy 5xx arrives as a transport error.** For a proxied request, a 5xx from
   the stub comes back through `ureq` as `Error::Transport`, so it is recorded as
   `connect_failure` (cooling the egress for 60 s) rather than `upstream_5xx`
   (30 s). Both cool the same axis; only the duration and the reason string
   differ. Flagged because the evidence row is what the reader recomputes.
3. **One integrated cooling test was withdrawn.** A wire-level "cooled egress is
   demoted on the next request" test kept depending on which candidate happened
   to be reachable first; it was replaced by `router::tests::
   a_cooling_egress_is_demoted_to_the_back_of_the_plan` and
   `a_cooling_entry_expires_after_its_window`, which are pure and deterministic.
   The wire-level cooling path is still exercised by
   `a_proxy_407_cools_the_egress_and_stops_the_chain`.
4. **`tests/gate_tunnel.rs` serialises its tests** behind a mutex: they share
   loopback stubs and a long response timeout, so parallel execution made them
   flaky for reasons unrelated to the gate.

### W4 record (2026-11-09, in progress -- M11 landed)

**M11: SSE pass-through, shipped.** The gate relays a `text/event-stream`
answer as it arrives; it buffers nothing, re-frames nothing and invents no
terminator.

- `transport::Outcome::Streaming { status, headers, body }` carries the live
  upstream reader when the upstream content type is `text/event-stream`, and
  `Outcome::Answered` stays the buffered path. Everything above the transport
  sees one `Outcome` enum, so a caller cannot tell from the status line which it
  got.
- `server::Body` is `Bytes | Stream`. A buffered answer renders with
  `Content-Length`; a stream renders the head and then relays `SSE_RELAY_CHUNK`
  reads, flushing each. The stream completes by closing the connection (the
  HTTP/1.0 rule), so no chunk framing is emitted and the upstream's bytes are
  the client's bytes.
- Cooling and fallback still apply **before** the first byte. A retryable status
  on a streaming answer walks the chain like any other; only a 2xx with no
  fallback opens the relay.
- A transport failure after the first byte closes the stream. The gate never
  fabricates `data: [DONE]`.

**Green.** `cargo test`: 221 unit tests, `g1_spike` (2), `gate_loopback` (6),
`gate_sse` (2) and `gate_tunnel` (3). Four consecutive full runs clean.

`gate_sse` proves byte equality (not "contains"), content-type preservation,
the evidence header on the stream head, `Connection: close` instead of a false
length, and that a non-stream answer still declares `Content-Length`. An
out-of-tree end-to-end run against the built binary passed 6/6.

**Deviations.**

1. **A stream has no `Content-Length` and no `Transfer-Encoding`.** The
   contract says the SSE path is a byte pass-through; chunked framing would
   re-frame it, which the contract forbids. The completion rule is therefore
   "close the connection at the end of the body", which every SSE client
   already handles.
2. **The relay chunk is 16 KiB**, not the 1 MiB per-event cap. The cap bounds
   one event the *upstream* may send; this is the socket read size, so a large
   `data:` line still streams without being buffered whole.

## 14. Immediate payoff

The core already takes `--base-url`, `--model` and `--key-env`. With a gate:

```bash
minicon-harness --root ./playground \
  --base-url http://127.0.0.1:8787/chat/completions \
  --model gate/planner \
  --key-env GATE_TOKEN \
  --task "..."
```

The core's `--base-url` is the **full endpoint URL**, not a version root:
`OPENAI_COMPATIBLE_CHAT_URL` is `https://api.deepseek.com/chat/completions`, and
the core posts to whatever that URL is. Naming `.../v1` would have it post to
`.../v1`. The gate answers both `/chat/completions` and `/v1/chat/completions`,
so a client that names either shape works; the core's tier
(`tests/gate_client.rs`) uses the full endpoint. `GATE_TOKEN` above is the
**gate** bearer: the core has one key and it authenticates the client to the
gate, which then presents the lane's credential upstream.

The harness stops knowing about providers, credentials, models or proxies. It
names an agent; the pool decides the rest. The same URL works for OpenCode
(`baseURL: http://127.0.0.1:8787/v1`) with no `HTTP_PROXY`, no per-provider
settings, and no OAuth inside the client.
